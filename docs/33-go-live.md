# 33 — الانتقال إلى الإنتاج: خطوات استقبال أول عميل يدفع

هذه ليست وثيقة معمارية. هذه **قائمة تنفيذ مرتّبة**: افعل هذا، ثم هذا، ثم تحقّق.
اقرأها من أعلى إلى أسفل ونفّذها بالترتيب، فالخطوات تعتمد على بعضها.

البوّابة النهائية في الخطوة ١١:

```bash
cd backend && npm run preflight
```

`⛔ حاجز` واحد يعني **لا تستقبل مالًا بعد**. السكربت يخرج بالرمز `1` عند وجود
حاجز، و`0` فيما عدا ذلك، فيصلح أن يكون شرطًا في أي نص آلي.

## ⚠️ الخطوات التي لا رجعة فيها

اقرأ هذا الجدول **قبل** أن تبدأ، لا بعد.

| الخطوة | لماذا لا رجعة فيها |
|---|---|
| تغيير `ENCRYPTION_KEY` بعد تخزين أي بيانات اعتماد | كل توكن قناة أو تكامل مخزَّن (واتساب، تيليجرام، سلة، زد) يصير **غير قابل للفك نهائيًا**. لا توجد أداة استرجاع. الحل الوحيد هو إعادة ربط كل قناة يدويًا. **اضبطه قبل ربط أول قناة، لا بعده.** |
| حذف بيانات العرض (الخطوة ١٠) | `DELETE` في SQL نهائي. لا سلّة محذوفات. النسخة الاحتياطية في الخطوة ٠ هي طريق الرجوع الوحيد. |
| تسجيل `OAUTH_REDIRECT_BASE` لدى سلة وزد | مسجَّل لديهم بنصّه الحرفي. تغييره لاحقًا **يتطلب إعادة تقديم الطلب ومراجعة جديدة**. ثبّت النطاق أولًا (الخطوة ٣). |
| إصدار فاتورة بنسبة ضريبة | `vat_halalas` مخزَّن على الفاتورة لا محسوب، والفاتورة الصادرة وثيقة. لا تُصدر فاتورة بنسبة ١٥٪ قبل التسجيل الضريبي الفعلي (الخطوة ٦). |
| `prisma migrate deploy` على الإنتاج | الهجرة تُطبَّق وتُسجَّل. التراجع عنها عملية يدوية بحتة. |

كل ما عدا ذلك في هذه الوثيقة هو ضبط متغيّر بيئة، ويُتراجع عنه بتغييره مجددًا.

## ٠) نسخة احتياطية — قبل أي شيء آخر

## ٢) الأسرار — `JWT_SECRET` و `ENCRYPTION_KEY`

**هذه أخطر خطوة في الوثيقة.** قيمة تطويرية معروفة هنا تعني أن أي شخص قرأ
المستودع يستطيع تزوير جلسة لأي مستخدم، أو فكّ تشفير كل توكنات القنوات.

**من أين تأتي القيمة:** ولّدها، لا تخترعها.

```bash
openssl rand -base64 32     # لـ JWT_SECRET
openssl rand -base64 32     # مرة أخرى، قيمة مختلفة، لـ ENCRYPTION_KEY
```

**اضبط على Render:**

```
JWT_SECRET      = <الناتج الأول>
ENCRYPTION_KEY  = <الناتج الثاني>
```

**التحقق:**
- الخدمة تقلع بعد إعادة التشغيل (لو كان أحدهما مفقودًا لما أقلعت أصلًا —
  `src/config/env.ts` يرمي عمدًا بلا قيمة افتراضية).
- `npm run preflight` يقول `✅ سليم` لكليهما مع الطول، ولا يقول
  «قيمته تطابق قيمة منشورة في `.env.example`».

> ⚠️ **لا رجعة:** غيّر `ENCRYPTION_KEY` **قبل** ربط أي قناة حقيقية. بعد ربط
> واتساب أو تيليجرام، تغييره يفقدك التوكنات المخزّنة نهائيًا.

> تغيير `JWT_SECRET` يُخرج كل من هو مسجّل دخول الآن. هذا مزعج، لا مدمّر.

## ٣) النطاق والروابط

الترتيب هنا مقصود: النطاق أولًا، لأن ثلاثة متغيّرات تشتقّ منه، وواحد منها
(`OAUTH_REDIRECT_BASE`) يُسجَّل لدى طرف ثالث فلا يُغيَّر بسهولة.

1. اشترِ النطاق.
2. Render → Settings → Custom Domain → أضِف نطاق الواجهة ونطاق الـ API.
3. اضبط سجلات DNS كما يعرضها Render، وانتظر ظهور شهادة TLS (`https` يعمل).
4. اضبط:

```
APP_URL              = https://app.<نطاقك>
CORS_ORIGIN          = https://app.<نطاقك>
OAUTH_REDIRECT_BASE  = https://api.<نطاقك>
```

**من أين تأتي القيم:**
- `APP_URL` = عنوان **الواجهة** كما يفتحه العميل في متصفحه. منه تُبنى روابط
  تأكيد البريد واستعادة كلمة المرور.
- `CORS_ORIGIN` = نفس أصل `APP_URL` بالضبط (البروتوكول + المضيف + المنفذ).
- `OAUTH_REDIRECT_BASE` = عنوان **الـ Backend**، لا الواجهة — مسار العودة من
  سلة وزد مسار خادم.

**التحقق:**
- افتح `https://app.<نطاقك>` — تفتح الواجهة، وتحمّل البيانات فعلًا (لو كان
  `CORS_ORIGIN` خاطئًا لظهرت الواجهة ثم بقيت فارغة، والخطأ في وحدة تحكّم
  المتصفح: `blocked by CORS policy`).
- اطلب استعادة كلمة مرور لحسابك، وافحص الرابط في الرسالة: يجب أن يبدأ بـ
  `https://app.<نطاقك>` لا بـ `localhost`.

> ⚠️ `APP_URL` بقيمة `localhost` لا يفشل بصوت عالٍ إطلاقًا: الرسالة تُرسل
> بنجاح، والرابط داخلها يشير إلى جهاز العميل نفسه. هذا حاجز في الفحص.

## ٤) البريد — Resend

بدون هذه الخطوة **لا رسالة واحدة تخرج من الخادم**: لا تأكيد بريد، ولا استعادة
كلمة مرور، ولا إشعار «شخص طلب باقة». المزوّد الافتراضي `console` يطبع الرسالة
في سجلّ الخادم ويتوقف.

**من أين تأتي القيم:**
1. أنشئ حسابًا على [resend.com](https://resend.com) (الخطة المجانية تكفي
   للبداية).
2. Domains → Add Domain → أدخل نطاقك → أضِف سجلات DNS التي يعرضها (SPF و
   DKIM) → انتظر حتى تصير الحالة **Verified**.
3. API Keys → Create API Key → انسخ القيمة **الآن** (لا تُعرض مرة ثانية).

**اضبط على Render:**

```
EMAIL_PROVIDER        = resend
RESEND_API_KEY        = re_...
EMAIL_FROM            = ميسور <onboarding@<نطاقك>>
PLATFORM_NOTIFY_EMAIL = <بريدك الشخصي>
```

**التحقق:**
- اطلب استعادة كلمة مرور لحسابك → تصل رسالة فعلية إلى صندوق بريدك.
- افتح صفحة الهبوط واملأ نموذج طلب الباقة ببريد تجريبي → يصلك إشعار على
  `PLATFORM_NOTIFY_EMAIL`، **و** يظهر الطلب في `/billing` داخل المنصة.

> نطاق `EMAIL_FROM` **يجب** أن يكون النطاق الموثّق في الخطوة ٢ أعلاه. الإرسال
> من نطاق غير موثّق يُرفض بالكامل، والتطبيق لا يرمي عند فشل الإرسال (بقصد:
> عطل عند مزوّد البريد يجب ألا يمنع التسجيل)، فالفشل صامت تمامًا.

> الطابور داخل المنصة (`/billing`) هو القناة **الأساسية** لطلبات الباقات
> ويعمل بلا بريد. `PLATFORM_NOTIFY_EMAIL` هو التنبيه فوقه — بدونه لا يضيع
> الطلب، لكن لا شيء يوقظك عند وصوله.

## ٥) المال — مزوّد الدفع

مزوّد الدفع الافتراضي **`contact`**: لا تُعرض أي بيانات بنكية داخل المنتج.
العميل يختار الباقة فتُصدر فاتورة، وتظهر له رسالة «سنتواصل معك» مع رقم
الفاتورة وزر واتساب. **أنت** تتصل به وتسلّمه بيانات السداد يدويًا، وعند وصول
المبلغ تفعّل باقته من `/billing`.

**اضبط على Render (كلاهما اختياري):**

```
BILLING_PROVIDER          = contact        # الافتراضي أصلًا — اضبطه صراحةً إن أردت
PLATFORM_CONTACT_WHATSAPP = 9665........   # أرقام فقط، بلا + وبلا مسافات
BILLING_VAT_PERCENT       = 0
```

**من أين يأتي `PLATFORM_CONTACT_WHATSAPP`:** رقم واتساب الذي تردّ عليه فعلًا،
بالصيغة الدولية وبلا `+`. غير مضبوط = يسقط إلى الرقم المنشور في صفحة الهبوط،
وهو افتراضي موثّق لا وهمي — فالزر يعمل ويصل إليك في الحالتين.

**التحقق:**
- `npm run preflight` → قسم «المال والفوترة» يقول
  `` `BILLING_PROVIDER` = `contact` `` وأن بيانات البنك **لا تُقرأ في هذا الوضع**.
- ادخل بحساب مالك منظمة → اختر باقة مدفوعة → **تأكد ألا يظهر أي آيبان على
  الشاشة**، وأن رقم الفاتورة وزر واتساب ظاهران، وأن الزر يفتح محادثة معك.

**عن `BILLING_VAT_PERCENT`:** اتركها `0` — وهي تنطبق على المزوّدين معًا.

> ⚠️ إصدار فاتورة بنسبة ١٥٪ قبل التسجيل الفعلي في هيئة الزكاة والضريبة
> والجمارك **مخالفة نظامية**، لأن الفاتورة الضريبية يجب أن تحمل رقم التسجيل
> الضريبي — ولا يوجد حقل لهذا الرقم في المنصة اليوم. ارفعها إلى `15` في اليوم
> الذي تُسجَّل فيه فعليًا، ولا تعدّل الفواتير الصادرة قبل ذلك اليوم.

### ٥-ب) الآيبان — **غير مطلوب مع مزوّد `contact`**

**تخطَّ هذا القسم كليًا ما دام `BILLING_PROVIDER` هو `contact`** (الافتراضي).
`BILLING_IBAN` و`BILLING_ACCOUNT_NAME` و`BILLING_BANK_NAME` **لا تُقرأ**، ولا
يفحصها `npm run preflight`، ولا تظهر في المنتج.

القسم باقٍ لأن نشرة قد تقرر لاحقًا نشر بيانات التحويل — والعودة إليها متغيّر
بيئة واحد لا كتابة كود:

```
BILLING_PROVIDER     = manual
BILLING_IBAN         = SA............................
BILLING_ACCOUNT_NAME = <اسم صاحب الحساب كما هو في البنك حرفيًا>
BILLING_BANK_NAME    = <اسم البنك>
```

**عند هذا التبديل — ولا شيء قبله — تعود فحوص الآيبان حواجز.** هذه الخطوة هي
سبب وجود سكربت الفحص: **إن لم تضبط هذه القيم مع `manual`، تعرض المنصة على عميل
يدفع آيبانًا وهميًا (`SA0000…`) مكتوبًا في الكود كقيمة افتراضية.**

**من أين تأتي القيم:** من تطبيق بنكك — «تفاصيل الحساب» / «معلومات الآيبان».
**انسخ الآيبان بزر النسخ، لا بالكتابة اليدوية.**

**التحقق:**
- `npm run preflight` يقول: `` `BILLING_IBAN` مضبوط وصالح شكلًا وتحققًا `` مع
  آخر ٤ خانات. طابق هذه الخانات الأربع بعينك مع تطبيق البنك.
- ادخل بحساب مالك منظمة → اختر باقة → تظهر شاشة التحويل: تأكد أن الآيبان
  والاسم والبنك هي حسابك أنت.

**عن `BILLING_ACCOUNT_NAME`:** البنوك السعودية ترفض التحويل إذا لم يطابق اسم
المستفيد الذي يكتبه المُرسِل اسمَ صاحب الحساب. اسم تقريبي هنا = تحويل مرفوض =
عميل يظن أن المنصة معطوبة.

> الفواتير المفتوحة لا تتأثر بالتبديل في أي اتجاه: كل فاتورة تحمل مزوّدها في
> صفّها، وشاشة الدفع تُبنى من قيمة الصفّ لا من متغيّر البيئة الحالي.

> ⚠️ إصدار فاتورة بنسبة ١٥٪ قبل التسجيل الفعلي في هيئة الزكاة والضريبة
> والجمارك **مخالفة نظامية**، لأن الفاتورة الضريبية يجب أن تحمل رقم التسجيل
> الضريبي — ولا يوجد حقل لهذا الرقم في المنصة اليوم. ارفعها إلى `15` في اليوم
> الذي تُسجَّل فيه فعليًا، ولا تعدّل الفواتير الصادرة قبل ذلك اليوم.

## ٦) التخزين الدائم

قرص Render يُستعاد عند كل إعادة تشغيل ونشر. مع `STORAGE_PROVIDER=local` يفقد
العميل **الملف الأصلي** لكل ما رفعه (النص المستخرج ناجٍ في قاعدة البيانات
فالبحث والردود تظل تعمل، لكن التنزيل يُجيب «الملف غير متوفر»).

**من أين تأتي القيم:** أنشئ حاوية على Cloudflare R2 (نحو دولار شهريًا) ثم:
R2 → Manage API Tokens → Create → انسخ المفتاحين.

```
STORAGE_PROVIDER   = s3
STORAGE_ENDPOINT   = https://<account-id>.r2.cloudflarestorage.com
STORAGE_BUCKET     = maysoor-knowledge
STORAGE_ACCESS_KEY = ...
STORAGE_SECRET_KEY = ...
STORAGE_REGION     = auto
```

**التحقق:** ارفع ملف PDF في قاعدة المعرفة → أعد تشغيل الخدمة من Render →
نزّل الملف نفسه. إن نزّل، فالتخزين دائم.

> خطأ إملائي في `STORAGE_PROVIDER` **يُفشل الرفع بصوت عالٍ** بدل السقوط
> الصامت إلى القرص المؤقت. هذا مقصود.

## ٩) مشرف المنصة — `is_platform_admin`

**لا يوجد أي مسار في الـ API يكتب هذا الحقل، وهذا تصميم مقصود لا نقص.**

السبب: `owner` هو أعلى دور **داخل** المنظمة. بعد فتح التسجيل الذاتي يصير كل
عميل `owner` على منظمته، فلو كان `owner` هو ما يحرس اعتماد التحويل البنكي
لاستطاع كل عميل تأكيد دفعته بنفسه ومدّ اشتراكه مجانًا. لذلك يُمنح هذا الحقل
بـ SQL يدويًا فقط.

**تشخيص أولًا:**

```sql
SELECT id, email, is_platform_admin FROM users WHERE is_platform_admin = true;
```

**المنح:**

```sql
-- ضع بريدك أنت. تأكد أن الحساب موجود وأن كلمة مروره ليست كلمة مرور البذور.
UPDATE users SET is_platform_admin = true WHERE email = 'you@example.com';
```

**السحب (عند الحاجة):**

```sql
UPDATE users SET is_platform_admin = false WHERE email = 'someone@example.com';
```

**التحقق:**

```sql
SELECT email FROM users WHERE is_platform_admin = true;
```

يجب أن يظهر **حساب واحد** — حسابك. كل حساب في هذه القائمة يقرأ فواتير **كل**
المنظمات ويستطيع اعتمادها. ثم ادخل بهذا الحساب: يجب أن تظهر لك صفحة الفواتير
الإدارية وطابور طلبات الباقات في `/billing`.

> بلا مشرف منصة واحد على الأقل، **لا أحد يستطيع اعتماد تحويل بنكي**: العميل
> يحوّل المال، ويرفع الإيصال، وتبقى الفاتورة `awaiting_review` إلى الأبد،
> ويبقى هو على الباقة المجانية. هذا حاجز في الفحص.

### ١٠-أ) الحسابان التجريبيان — حاجز

`manager@albayan.demo` و `agent@albayan.demo` كلمات مرورهما **مكتوبة ومطبوعة
في `prisma/seed.ts` داخل مستودع عام**. أي شخص قرأ المستودع يستطيع تسجيل
الدخول بهما على أي نشرة بُذرت يومًا.

**تشخيص:**

```sql
SELECT id, email, status, is_platform_admin
FROM users
WHERE email IN ('manager@albayan.demo', 'agent@albayan.demo');
```

**الحذف** — بالترتيب، فالمفاتيح الأجنبية `RESTRICT` وليست `CASCADE`. استبدل
`you@example.com` ببريدك (تنتقل إليه ملكية ما أنشأه هذان الحسابان):

```sql
BEGIN;

-- ١. نقل ما يملكانه إليك (الأعمدة NOT NULL، فلا يمكن تركها فارغة)
UPDATE knowledge_sources SET created_by = (SELECT id FROM users WHERE email = 'you@example.com')
 WHERE created_by IN (SELECT id FROM users WHERE email IN ('manager@albayan.demo','agent@albayan.demo'));

UPDATE simulation_links SET created_by = (SELECT id FROM users WHERE email = 'you@example.com')
 WHERE created_by IN (SELECT id FROM users WHERE email IN ('manager@albayan.demo','agent@albayan.demo'));

UPDATE user_store_roles SET granted_by = (SELECT id FROM users WHERE email = 'you@example.com')
 WHERE granted_by IN (SELECT id FROM users WHERE email IN ('manager@albayan.demo','agent@albayan.demo'));

-- ٢. أدوارهما وعضويتهما
DELETE FROM user_store_roles
 WHERE user_id IN (SELECT id FROM users WHERE email IN ('manager@albayan.demo','agent@albayan.demo'));

DELETE FROM organization_members
 WHERE user_id IN (SELECT id FROM users WHERE email IN ('manager@albayan.demo','agent@albayan.demo'));

-- ٣. الحسابان نفساهما
DELETE FROM users WHERE email IN ('manager@albayan.demo','agent@albayan.demo');

-- ٤. تأكّد قبل الاعتماد — يجب أن تكون النتيجة 0
SELECT count(*) FROM users WHERE email LIKE '%@albayan.demo';

COMMIT;   -- لو ظهر أي شيء غير متوقع أعلاه: اكتب ROLLBACK; بدلًا منه
```

بقية الجداول التي تشير إليهما (`messages.sender_user_id`، `tickets`،
`ticket_events`، `audit_logs`، `conversations`) قاعدتها `SET NULL`، فتتحوّل
تلقائيًا إلى «بلا مُرسِل» ويبقى المحتوى.

### ١٠-ب) كلمة مرور حسابك أنت

حساب المالك المُنشأ من البذور له أيضًا كلمة مرور منشورة في `prisma/seed.ts`.
**غيّرها من داخل المنصة** (الإعدادات → كلمة المرور)، لا بـ SQL: تغييرها من
التطبيق يرفع `token_version` فيُلغي كل جلسة مفتوحة لذلك الحساب فورًا.

`npm run preflight` يفحص هذا بمقارنة تشفيرية (`bcrypt.compare`) مع القيم
المقروءة من `prisma/seed.ts`، **ولا يطبع كلمة المرور ولا يسجّلها** — يطبع
البريد الذي يجب تغيير كلمته فقط.

### ١٠-ج) المحادثة والعميل الوهميان — تحذير

محادثة «سارة العتيبي» ومقاطع المعرفة التجريبية تراكمت من نشرات سابقة كانت
تعيد تشغيل البذور في كل مرة. السكربت الجاهز:

```bash
psql "$DATABASE_URL" -f cleanupdemodata.sql   # اقرأه أولًا: قسم التشخيص ثم قسم الحذف
```

شغّل **قسم التشخيص وحده أولًا**، واقرأ ما يعرضه، ولا تشغّل قسم الحذف إلا بعد
أن تتأكد أن المعروض هو المحتوى الوهمي لا محتوى حقيقي أضفته لاحقًا.

### ١٠-د) المتاجر التجريبية الستة — تحذير، والأرجح ألا تحذفها

كل الجداول التي تشير إلى `stores` قاعدتها `RESTRICT`، فحذف متجر واحد يعني
حذف محادثاته ورسائله وعملائه ومعرفته وتذاكره وسجلّاته بالترتيب الصحيح — عملية
يدويّة طويلة وخطرة.

**الأفضل عمليًا:** أعد تسميتها لتصبح متاجرك الحقيقية بدل حذفها. أحد هذه
المتاجر **هو متجرك الحقيقي فعلًا** بعد إعادة التسمية — فتأكّد أيّها قبل أن
تلمس شيئًا:

```sql
SELECT id, name, slug, created_at FROM stores ORDER BY created_at;
```

هذا بند تحذير في الفحص لا حاجز: وجود متاجر فارغة لا يؤذي عميلًا يدفع.

## ١١) البوّابة: `npm run preflight`

### الطريقة الأولى (المفضّلة) — على Render نفسه

Render → خدمة الـ Backend → **Shell**:

```bash
cd backend && npm run preflight
```

هذه الطريقة تقرأ **التهيئة الجارية فعلًا** في الإنتاج — وهذا بالضبط ما نريد
فحصه، لا نسخة منها على جهازك.

### الطريقة الثانية — من جهازك

انسخ القيم من Render → Environment، وصدّر **كل متغيّر في جملة `export`
منفصلة**:

```bash
cd backend
export DATABASE_URL="postgresql://..."
export DIRECT_DATABASE_URL="postgresql://..."
export JWT_SECRET="..."
export ENCRYPTION_KEY="..."
# ... بقية المتغيّرات
npm run preflight
```

> ⚠️ لا تكتب `export A=x B=$A` في سطر واحد: الصدفة توسّع `$A` **قبل** إسناده،
> فيصل المتغيّر الثاني فارغًا وتظنّ أنك ضبطته.

### كيف تقرأ النتيجة

| العلامة | المعنى | ماذا تفعل |
|---|---|---|
| `⛔ حاجز` | عميل يخسر ماله، أو لا يصله بريد، أو يرى شيئًا معطوبًا | **أصلحه.** لا تستقبل مالًا قبل ذلك |
| `⚠️ تحذير` | يعمل، لكنه محرج أو خطر | اقرأه واتّخذ قرارًا واعيًا. الإطلاق ممكن معه |
| `❔ تعذّر` | لم يُفحَص (قاعدة البيانات غير متاحة مثلًا) | **ليس حكمًا بالسلامة.** أعد التشغيل حيث يمكن الفحص |
| `✅ سليم` | لا شيء تفعله | — |

الخلاصة في آخر المخرجات، ورمز الخروج `1` عند وجود حاجز و`0` فيما عدا ذلك.

**السكربت لا يكتب في قاعدة البيانات إطلاقًا**، فتشغيله على الإنتاج آمن، وتشغيله
مرارًا آمن. ولا يطبع أي سرّ: يبلّغ عن الوجود والطول وهل القيمة تساوي قيمة
منشورة في المستودع، ومن الآيبان يطبع آخر ٤ خانات فقط.

## ١٢) تجربة الدورة كاملة قبل العميل الحقيقي

نفّذها بحسابك على منظمة تجريبية، ثم احذف الفاتورة الناتجة أو اتركها ملغاة.

### مع المزوّد الافتراضي `contact`

1. ادخل بحساب مالك منظمة → صفحة الباقات → اختر باقة مدفوعة.
2. تظهر شاشة «سنتواصل معك»: **تحقّق ألا يظهر أي آيبان**، وأن رقم الفاتورة
   ظاهر وقابل للنسخ، وأن زر واتساب يفتح محادثة على رقمك أنت.
3. مثّل دورك: اتصل بالعميل (أو راسله) وسلّمه بيانات السداد يدويًا.
4. بعد وصول المبلغ: ادخل بحساب **مشرف المنصة** → `/billing` → طابور الطلبات →
   **فعّل الباقة** للمنظمة (اختر الباقة وعدد الفترات والمبلغ المُحصَّل فعلًا).
5. تحقّق: صدرت فاتورة `paid` بالمبلغ الذي كتبته، والاشتراك تمدّد، والحدود
   الجديدة سارية على المنظمة.

> التفعيل يكتب فاتورة `paid` **دائمًا**، لا يكتفي بتفعيل الاشتراك: اشتراك
> فعّال بلا فاتورة خلفه لا يُميَّز عن ثغرة ترقية مجانية، ولا يترك أي جواب
> دائم عن «ماذا دفع هذا العميل ومتى» بعد أن تختفي محادثة واتساب.

### مع `BILLING_PROVIDER=manual` فقط

1. اختر باقة مدفوعة → تظهر شاشة التحويل: **تحقّق أن الآيبان والاسم والبنك هي
   حسابك أنت**، وأن هناك **رقمًا مرجعيًا** (رقم الفاتورة).
2. حوّل مبلغًا رمزيًا فعليًا (ريالًا واحدًا) إلى حسابك من حساب آخر، واكتب
   الرقم المرجعي في خانة الملاحظات.
3. ارفع الإيصال من صفحة الفواتير → تصير الفاتورة `awaiting_review`.
4. ادخل بحساب **مشرف المنصة** → `/billing` → اعتمد الفاتورة.
5. تحقّق: الفاتورة `paid`، والاشتراك تمدّد، والحدود الجديدة سارية على المنظمة.

> الرقم المرجعي **إلزامي** في هذا المسار: تحويل بلا مرجع لا يمكن ربطه بفاتورة.
> إن وصلك تحويل بلا مرجع، اسأل العميل عن المبلغ والتاريخ واعتمدها يدويًا.

## ١٣) بعد أول عميل

| كل | افعل |
|---|---|
| بعد كل تعديل على متغيّرات Render | `npm run preflight` |
| أسبوعيًا | افتح Sentry — ليس كل خطأ يشتكي منه العميل |
| شهريًا | تأكّد أن النسخ الاحتياطية التلقائية تعمل |
| كل ربع سنة | **استعادة اختبارية فعلية** (الخطوة ٠) |
| عند تغيير رقم واتساب التواصل | `PLATFORM_CONTACT_WHATSAPP` ثم `npm run preflight` — القيمة تُقرأ عند كل طلب، فإعادة التشغيل تكفي ولا حاجة لنشر |
| عند تغيير الحساب البنكي (مع `manual` وحده) | `BILLING_IBAN` ثم `npm run preflight` فورًا — نفس المنطق: قراءة عند كل طلب |
| عند التسجيل الضريبي | `BILLING_VAT_PERCENT=15`، ولا تعدّل الفواتير الصادرة قبل ذلك |
