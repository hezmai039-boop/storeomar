# 37 — توصيف «Universal Omnichannel Platform»: الحكم والخطة

**الخلاصة: لا تُنفَّذ كما هي مكتوبة.** أكثر من نصفها **مبني عندك بالفعل**،
وجزء منها **غير موجود في الواقع**، والباقي **سابق لأوانه بعميل واحد**.
الفجوة الحقيقية **بند واحد** — وهو محجوز خلف موافقة من ميتا لا يفتحها كود.

---

## ١ — ما هو مبني بالفعل (لا تدفع ثمنه مرتين)

| ما يطلبه التوصيف | الحالة | أين |
|---|---|---|
| Plugin/Connector لكل قناة | ✅ **مبني** | `channels/adapters/types.ts` + `registry.ts` — ٨ محوّلات |
| واجهة موحّدة للمحوّلات | ✅ **مبني** | `verifyWebhookSignature` · `parseWebhook` · `sendMessage` |
| Unified Event / Message Bus | ✅ **مبني** | `NormalizedInboundMessage` — كل قناة تُطبَّع قبل دخول النظام |
| OAuth رسمي + `oauth_states` | ✅ **مبني** | `integrations/oauth/` — حالة أحادية الاستخدام، مطالبة ذرّية، انتهاء صلاحية |
| Token Manager (تشفير/تجديد/انتهاء) | ✅ **مبني** | `tokenRefresh.ts` + `lib/crypto` (AES) + `tokenExpiresAt` |
| «لا Token إلى Frontend» | ✅ **مبني** | كل مسار يحذف `credentialsEncrypted` قبل الإرجاع |
| Webhook Engine + تحقّق التوقيع | ✅ **مبني** | `channels/webhook.ts` + `metaSignature.ts` (HMAC قبل أي كتابة) |
| Health Check + تشخيص | ✅ **مبني** | `channelHealth.ts` + `diagnostics.ts` + `metaErrors.ts` |
| Multi-tenant معزول | ✅ **مبني** | RLS على `app.accessible_store_ids` — مُختبَر |
| Audit Logs | ✅ **مبني** | `lib/audit.ts` على كل تغيير |
| RBAC | ✅ **مبني** | owner / store_manager / agent + صلاحيات لكل مسار |
| Rate Limiting · CSRF · OAuth State | ✅ **مبني** | محدّدات لكل مسار + حالة أحادية الاستخدام |
| صفحة Integrations بالبطاقات | ✅ **مبني** | مع الحالة وآخر مزامنة وإعادة الربط |
| تنبيه عند تعطّل قناة | ✅ **مبني** | `lastError` + `lastErrorAt` + لوحة المالك |

**ثلاثة عشر بندًا من التوصيف موجودة اليوم.** إعادة بنائها باسم جديد
(`MetaConnector`, `channel_messages`, `tenant_channels`) ليست ترقية — هي
هجرة بيانات على منصة فيها عميل ينتظر.

---

## ٢ — ما ليس حقيقيًا

**سناب شات:** لا توجد واجهة رسائل أعمال عامة تسمح لطرف ثالث بالرد على رسائل
العملاء. Snap Kit و Ads API شيء آخر تمامًا. **لا يمكن بناؤه.**

**تيك توك:** واجهة الرسائل مغلقة ومحصورة بشركاء مُختارين وبمناطق محددة.
المحوّل موجود عندك (`adapters/tiktok.ts`) لكنه لا يُفعَّل بلا وصول ممنوح.

**Google Business Messages:** **أُغلقت من جوجل نهائيًا** — لم تعد خيارًا.

التوصيف نفسه يقول «إذا كانت متاحة… وإلا اعرض أنها غير مدعومة». الجواب الصادق:
**غير متاحة**، والبناء لها اليوم كتابة كود ميت.

---

## ٣ — الفجوة الحقيقية الوحيدة

> «ممنوع… حلول تعتمد على نسخ التوكنات يدوياً.»

هذه **محقّة**، وهي المكان الوحيد الذي ما زال المنتج يخالفها:
`POST /channel-accounts` يستقبل `credentials` ملصوقة يدويًا. أي أن ربط واتساب
لكل عميل يمرّ عبرك أنت داخل Meta.

الحل اسمه **Meta Embedded Signup** — التاجر يضغط زرًّا، يسجّل دخوله بحسابه هو،
فتصلنا تلقائيًا: Business ID · WABA ID · Phone Number ID · Page ID · Instagram
ID · Access Token · الويبهوك.

**هذا هو البند الوحيد الذي يستحق البناء من التوصيف كله.**

### لكنه محجوز خلف بوّابة لا يفتحها كود

Embedded Signup **يتطلّب أن تكون Tech Provider أو Solution Partner** لدى ميتا،
وبعدها **App Review** و**Advanced Access** للصلاحيات. والنص صريح:

> إن لم تُمنح Advanced Access لصلاحية ما، **فإنها لا تظهر في تدفّق Embedded
> Signup أصلًا**.

ويضاف إلى ذلك موعد حاسم:

> **Embedded Signup v2 يُلغى في ١٥ أكتوبر ٢٠٢٦.**

أي أن أي بناء اليوم **يجب أن يكون v4 مباشرة** — بناء v2 الآن عمل يُرمى خلال
أسابيع.

**الفرق بين المسارين يخصّك ماليًا:**

| | Tech Provider | Solution Partner |
|---|---|---|
| من يدفع لميتا | **العميل مباشرة** | **أنت**، ثم تُحصّل منه |
| خط ائتمان من ميتا | لا | نعم |
| ما تفوتره أنت | اشتراك منصتك فقط | الاشتراك + استهلاك الرسائل |

**Tech Provider هو الصحيح لك الآن**: لا تتحمّل فاتورة رسائل عملائك، ولا تحتاج
خط ائتمان، ولا تدخل في تحصيل استهلاك متغيّر — وأنت لم تُصدر فاتورة واحدة بعد.

---

## ٤ — الخطة، مرتّبة بالأثر لا بالحجم

**اليوم — مجاني، وهو أطول مسار زمني:**
تقدّم بطلب **Meta Tech Provider**. الموافقة تستغرق أيامًا إلى أسابيع، ولا
يختصرها أي كود. كل يوم تأخير هنا يوم تأخير في كل ما بعده. ابدأ به قبل أي سطر.

**بالتوازي (لا ينتظر ميتا):**
مارينز يعمل **اليوم** بالمسار اليدوي. عميل واحد لا يحتاج Embedded Signup —
يحتاج رقمًا يعمل. ولا تنسَ أن **تيليجرام يعطي نفس السرعة بصفر إجراءات ميتا**.

**بعد الموافقة:** ابنِ موفّر Meta فوق آلة OAuth الموجودة — نفس `oauth_states`،
نفس `tokenRefresh`، نفس التشفير. العمل الحقيقي هو تبادل الرمز وجلب الأصول
وتسجيل الويبهوك، لا بنية تحتية جديدة.

**مؤجّل حتى يطلبه عميل يدفع:** Slack · Discord · LINE · Viber · Outlook ·
Gmail · SMS. كل محوّل بلا عميل هو كود ميت يحتاج صيانة. القاعدة: **العميل يسبق
المحوّل.**

**لا يُبنى:** Message Bus منفصل · Dead Letter Queue · Tracing · جداول
`tenant_channels`/`channel_messages` الموازية. هذه حلول لمشكلة حجم لا تملكها،
وثمنها هجرة بيانات على منصة حيّة.

## ٥ — ما نُفِّذ فعلًا في هذه الجولة

مراجعة التوصيف كشفت **ثغرة حقيقية** في مسار OAuth القائم:

`getOAuthProvider()` كان فهرسة مباشرة على كائن حرفي، فيمشي في سلسلة النماذج.
`providers["__proto__"]` يُعيد كائنًا و`["constructor"]` يُعيد دالة —
**كلاهما صادق منطقيًا**، فيمرّان من `if (!provider)` ثم ينهاران على
`provider.isConfigured is not a function`.

و`:platform` يأتي من الرابط مباشرة، **وأحد موضعَي الاستدعاء هو مسار الـ
callback العام**. أي خطأ ٥٠٠ يُطلقه أي عابر بكتابة رابط، على المسار الذي
يتعامل مع بيانات اعتماد التجّار.

مُصلَح بـ`Object.hasOwn`، ومعه اختبار **أُثبت أنه يفشل بلا الإصلاح ويمرّ معه**
— لا اختبار يرافق الكود ويؤكّده.

وهي نفس الثغرة التي كشفها اختبار القوالب في `docs/36`. **نمط واحد، موضعان،
كلاهما مُغلق الآن.**
