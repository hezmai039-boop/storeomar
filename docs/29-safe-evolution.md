# 29 — التطوير الآمن بعد وجود عملاء مشتركين

> **القاعدة الحاكمة:** بعد أول عميل يدفع، لم يعد السؤال «هل تعمل الميزة الجديدة؟» بل **«هل يستمر كل شيء قديم في العمل أثناء إضافتها؟»**

---

## ✅ الخطر الأول — كان: لا توجد هجرات. حُلَّ.

> هذا القسم كان يفتح بـ «🔴 أخطر نقطة في المشروع». لم يعد كذلك، وتُرك مكتوبًا
> بدل حذفه لأن معرفة *لماذا* صار الوضع آمنًا هي ما يمنع العودة إلى الخلف.

**ما كان:** لا مجلد `prisma/migrations` إطلاقًا، وتغيير المخطط بـ `db push` —
وهو أمر يجعل القاعدة تطابق المخطط **بأي وسيلة بما فيها الحذف**. إعادة تسمية
عمود = حذف وإنشاء = فقدان كل ما فيه، بلا سجلّ ولا تراجع.

**ما صار:** مجلد هجرات حقيقي، و`docker-entrypoint.sh` يشغّل `migrate deploy`
لا `db push`. أربع هجرات مطبَّقة، وكل تغيير لاحق يُضاف ملفًا جديدًا.

| | قبل | بعد |
|---|---|---|
| أداة التغيير | `db push` | `migrate deploy` |
| سجلّ ما طُبِّق | لا شيء | جدول `_prisma_migrations` |
| التراجع | مستحيل | ملف SQL معكوس |
| قاعدة موجودة بلا سجلّ | تتعطّل | `ensure-baseline.ts` يعالجها تلقائيًا |

### القاعدة الآن

```bash
npx prisma migrate dev --name وصف_مختصر    # محليًا: ينشئ الملف
npx prisma migrate deploy                   # الإنتاج: يطبّق المعلّق فقط
```

🔴 **لا تشغّل `db push` على الإنتاج بعد اليوم، ولا تعدّل ملف هجرة مطبَّقة.**
Prisma يخزّن بصمة (checksum) لكل ملف؛ تعديل ملف مطبَّق يجعل كل نشر تالٍ يفشل.
التصحيح يكون بهجرة **جديدة**.

### الهجرات الإضافية تُكتب بـ `IF NOT EXISTS`

ليس تجميلًا: الهجرات تنزل على قواعد بُنيت أصلًا بـ `db push`، وقد يكون عمود
موجودًا سلفًا. إعادة إضافته تُفشل الهجرة كاملة وتُسجَّل كفاشلة، فتُحجب كل نشرة
بعدها — من أجل تغيير إضافي كل ما يريده هو «ليكن هذا العمود موجودًا».

---

## 🔒 بروفة على نسخة من الإنتاج — قبل الإنتاج

أخطر تغيير ليس الذي يفشل، بل الذي **ينجح على قاعدة فارغة ويفشل على قاعدة فيها
بيانات حقيقية**: قيد فريد يصطدم بصفّين متطابقين، أو عمود يصير إلزاميًا وفيه
صفوف فارغة. قاعدتك المحلية لن تكشف أيًّا منهما.

```bash
./scripts/backup.sh "$DATABASE_URL"                 # نسخة من الإنتاج
./scripts/restore-to-staging.sh ./backups/maysoor-*.dump   # نسخة للتجربة
# طبّق التغيير على النسخة، وشغّل عليها، وتأكّد
npx prisma migrate deploy                            # ثم الإنتاج
```

⚠️ ملف النسخة يحوي **كل بيانات عملائك** وبيانات اعتماد قنواتهم مشفّرة. مستثنى
من Git، ولا يُرفع إلى تخزين عام أبدًا.

## نمط «توسيع ثم تقليص» — لكل تغيير مخطط

لا تغيّر عمودًا موجودًا مباشرة أبدًا. اتبع ثلاث مراحل، كل واحدة تُنشر وحدها:

```
1. توسيع   أضف الجديد (اختياريًا). القديم والجديد يعملان معًا.
              ↓ انشر · تأكد أن كل شيء سليم
2. ترحيل   انسخ البيانات. اكتب في الاثنين، اقرأ من الجديد.
              ↓ انشر · راقب أيامًا
3. تقليص   احذف القديم بعد التأكد أن لا شيء يقرؤه.
```

**مثال — إعادة تسمية `Store.name` إلى `Store.displayName`:**

❌ **خطأ:** تغيّر الاسم في `schema.prisma` وتشغّل `db push` → كل أسماء المتاجر تُمحى.

✅ **صحيح:** أضف `displayName` اختياريًا → انسخ القيم → اجعل الكود يكتب في الاثنين ويقرأ من الجديد → بعد أسبوع احذف `name`.

بطيء؟ نعم. لكنه **الفرق بين نشرة عادية ومكالمة من عميل يسأل لماذا اختفى اسم متجره.**

## ما هو آمن بالفعل بحكم التصميم ✅

هذه ليست مصادفة — بُنيت هكذا عمدًا:

### ١. سجلات المحوّلات (Adapter Registries)

خمسة أنظمة تتبع نفس النمط:

```
channels/adapters/      واتساب · إنستغرام · ماسنجر · تيليجرام · تيك توك
integrations/adapters/  سلة · زد · شوبيفاي · ووكومرس
billing/adapters/       manual  (moyasar لاحقًا)
lib/email/              console · resend
lib/storage/            local · s3
```

**إضافة أي مزوّد جديد = ملف واحد + سطر في السجل.** لا يتغيّر أي مسار ولا أي جدول ولا أي شاشة. عميل يستخدم واتساب لا يتأثر إطلاقًا بإضافة تيليجرام.

### ٢. `null` تعني «بلا حد» في الباقات

`maxStores: null` ليست صفرًا. إضافة باقة مؤسسية لاحقًا لا تحتاج أرقامًا وهمية مثل `999999` تُقرأ لاحقًا كخطأ.

### ٣. الأعمدة الجديدة اختيارية

`inputTokens` و`costMicroUsd` و`emailVerifiedAt` و`tokenExpiresAt` كلها `nullable` — الصفوف القديمة صالحة كما هي، ولا حاجة لتعبئة رجعية.

### ٤. الميزات خلف مفاتيح تشغيل

`advancedIntelligenceEnabled` لكل متجر. الميزة الجديدة **مغلقة افتراضيًا**، تفتحها لمتجر واحد وتراقب.

### ٥. البذور خاملة (idempotent)

كل شيء `upsert` مع `update: {}`. إعادة تشغيل `npm run seed` على الإنتاج **لا تدهس بيانات عميل**.

### ٦. تجاوز الحصة لا يقطع الخدمة

المتجر المتجاوز لا يُرد عليه آليًا، لكن رسالة زبونه **تُحفظ وتتحوّل تذكرة**. حالة الفوترة لا تبدو للزبون النهائي كعطل أبدًا.

## أثناء النشر: النسختان تعملان معًا

Render ينشر تدريجيًا — لدقائق يعمل **الكود القديم والجديد في آنٍ واحد**، وقد يكون متصفح العميل يحمل واجهة قديمة تنادي واجهة برمجية جديدة.

**لذلك:**

| ✅ افعل | ❌ لا تفعل |
|---|---|
| أضف حقلًا جديدًا للاستجابة | تحذف حقلًا موجودًا |
| أضف مسارًا جديدًا | تعيد تسمية مسار |
| اجعل الحقل الجديد اختياريًا في الطلب | تجعل حقلًا إلزاميًا |
| وسّع قيم `enum` | تضيّقها |

حذف حقل يحتاج نفس دورة «توسيع–تقليص»: أوقف استخدامه، انشر، انتظر، ثم احذفه.

## جدول RLS — لا تنسه أبدًا

كل جدول جديد فيه `store_id` **يجب** أن يُضاف إلى `prisma/rls.sql`:

```sql
tables text[] := array[
  'conversations', 'messages', ...,
  'your_new_table'          -- ← هنا
];
```

**نسيانه = تسريب بيانات بين المتاجر.** الجدول سيعمل بشكل ممتاز في الاختبار (متجر واحد)، ويكشف كل شيء في الإنتاج.

### الاستثناءات — وكلها موثّقة في `rls.sql` نفسه

| الجدول | لماذا لا سياسة له |
|---|---|
| جداول الفوترة الأربعة | بلا `store_id` أصلًا؛ عزلها من `req.auth.organizationId` (`docs/25`) |
| `oauth_states` | يُقرأ في callback عام بلا جلسة — سياسة تعتمد على السياق لن تطابق شيئًا وستُعطّل ربط كل تاجر. محميّ بسرّه العشوائي أحادي الاستخدام |
| `user_store_roles` | يُقرأ لحساب السياق نفسه — سياسة تعتمد عليه تكون دائرية وتمنع الجميع |

⚠️ **القاعدة ليست «أضف كل جدول»، بل «أضف كل جدول أو وثّق سبب الاستثناء في `rls.sql`».** إضافة سياسة لأحد هذين الجدولين تكسر تدفقًا يعمل — وهذا ما يجعل التوثيق في مكانه أهم من القاعدة المجرّدة.

## قائمة ما قبل أي تغيير

```
□ هل التغيير حاذف؟ → استخدم توسيع–تقليص
□ نسخة احتياطية مأخوذة ومُختبَرة الاستعادة؟
□ جدول جديد فيه store_id → أُضيف إلى rls.sql؟
□ حقل جديد → nullable؟
□ ميزة كبيرة → خلف مفتاح تشغيل؟
□ البذور ما زالت idempotent؟
□ 117 اختبارًا تمر + tsc نظيف في الطرفين؟
□ جُرِّب على قاعدة بيانات حقيقية لا اختبارات وحدة فقط؟
```

آخر بند مكتسب من تجربة فعلية: خلل `pg_advisory_xact_lock` كان يُرجع **500 في كل اشتراك**، ولم يلتقطه `tsc` ولا الـ117 اختبارًا — التقطه تشغيل واحد أمام PostgreSQL حقيقي.

## التوسّع الأفقي — جاهز مسبقًا

عند تجاوز نسخة واحدة من الخادم، اضبط `REDIS_URL` فقط:

- حدود المعدل تصبح مشتركة (بدونها N نسخة = N أضعاف الحد)
- سجلات عدم التكرار مشتركة (بدونها **رد مكرر للعميل** عند إعادة إرسال واتساب)
- تحديثات الوارد اللحظية تصل لكل النسخ

وانقطاع Redis **لا يُسقط المنصة** — يعود تلقائيًا لذاكرة النسخة الواحدة (`docs/08`).

| الجانب | الحالة |

| إضافة قنوات ومزوّدين | ✅ آمن بالتصميم |
