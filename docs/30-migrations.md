# 30 — الهجرات (Migrations)

## ما تغيّر

كان تغيير المخطط يتم بـ `prisma db push`، وهو يجعل قاعدة البيانات مطابقة للمخطط **بأي وسيلة بما فيها الحذف** — وإعادة تسمية عمود = حذف + إنشاء = فقدان بياناته، بلا سجل ولا تراجع.

الآن يوجد `prisma/migrations/`، وكل تغيير مخطط يصبح ملف SQL **مقروءًا ومراجَعًا ومسجّلًا**.

---

## خط الأساس

```
prisma/migrations/0_init/migration.sql    ← 941 سطرًا · 39 جدولًا
```

يمثّل المخطط الكامل كما هو اليوم. **تم التحقق منه فعليًا:**

| الفحص | النتيجة |
|---|---|
| `migrate deploy` على قاعدة فارغة | ✅ نجح |
| فحص الانحراف بعده | ✅ «هجرة فارغة» — لا فرق عن المخطط |
| مقارنة الجداول مع قاعدة `db push` | ✅ متطابقة (39 مقابل 39 + جدول التتبّع) |
| `apply-rls` ثم `seed` فوقها | ✅ نجحا |

---

## 🔴 خطوة لمرة واحدة على الإنتاج

قاعدة بيانات الإنتاج **مبنية أصلًا** بـ `db push`، فجداولها موجودة لكن Prisma لا يعرف ذلك. تشغيل `migrate deploy` عليها مباشرة سيحاول إنشاء جداول موجودة **ويفشل**.

الحل: أخبر Prisma أن خط الأساس مطبَّق فعلًا — **بلا لمس أي جدول**:

> النسخ الاحتياطية صارت تُسمّى `maysoor-*.dump` بعد إعادة التسمية. إن كنت
> تحتفظ بملفات أقدم باسم `atlas-*.dump` فهي صالحة كما هي، و
> `restore-to-staging.sh` يقبلها بلا إعادة تسمية.

```bash
# 1) نسخة احتياطية أولًا. غير قابل للتفاوض.
./scripts/backup.sh "$DATABASE_URL"
./scripts/restore-to-staging.sh ./backups/maysoor-<...>.dump

# 2) جرّبها على النسخة المستعادة أولًا
export DATABASE_URL="postgresql://.../maysoor_staging"
npm run prisma:baseline
npm run prisma:migrate     # يجب أن يقول: No pending migrations

# 3) ثم على الإنتاج، مرة واحدة فقط
export DATABASE_URL="<عنوان الإنتاج>"
npm run prisma:baseline
```

`prisma:baseline` يكتب صفًا واحدًا في `_prisma_migrations` يقول «0_init مطبَّق». **لا ينشئ ولا يحذف ولا يعدّل أي جدول.**

> ⚠️ نفّذها **مرة واحدة فقط** لكل قاعدة بيانات.

## سير العمل بعد ذلك

### تغيير مخطط جديد

```bash
# 1) عدّل prisma/schema.prisma
# 2) ولّد الهجرة وطبّقها محليًا
npm run prisma:migrate:dev -- --name add_something

# 3) راجع ملف SQL الناتج قبل رفعه — هذا هو بيت القصيد
cat prisma/migrations/*_add_something/migration.sql
```

**راجع الـ SQL دائمًا.** هذه هي اللحظة التي ترى فيها `DROP COLUMN` قبل أن تصل للإنتاج، لا بعدها.

### النشر

```bash
npm run deploy:db     # migrate + apply-rls + seed
```

الترتيب مقصود: الهجرة تنشئ الجداول، ثم RLS يضع سياسات العزل عليها، ثم البذور تملأ البيانات المرجعية. **عكسه يترك جدولًا جديدًا بلا سياسة عزل** — أي مكشوفًا بين المتاجر.

### فحص الانحراف

```bash
npm run db:drift
```

«هجرة فارغة» = القاعدة تطابق المخطط. أي شيء آخر يعني أن أحدهم عدّل القاعدة يدويًا.

---

## القواعد

**١. لا تشغّل `db push` على الإنتاج بعد الآن.** صارت أداة تجريب محلي فقط.

**٢. لا تعدّل ملف هجرة مرفوعًا.** Prisma يخزّن بصمة لكل ملف؛ تعديل ملف مطبَّق يجعل النشر يفشل. أنشئ هجرة جديدة تصحّح.

**٣. أي تغيير حاذف يمرّ بـ «توسيع–تقليص»** (`docs/29`): أضف الجديد → انقل البيانات → احذف القديم في نشرة لاحقة.

**٤. RLS ليس جزءًا من الهجرات.** `prisma/rls.sql` يُطبَّق بسكربت منفصل خامل يُعاد تشغيله بأمان. **جدول جديد فيه `store_id` يجب أن يُضاف إليه يدويًا** — نسيانه يسرّب بيانات بين المتاجر، ولن يظهر في اختبار بمتجر واحد.

---

## الخلاصة

| قبل | بعد |
|---|---|
| `db push` قد يحذف بصمت | ملف SQL مراجَع قبل التطبيق |
| لا سجل لما طُبِّق | `_prisma_migrations` يسجّل كل شيء |
| لا تراجع | كل تغيير هجرة قائمة بذاتها |
| `prisma:migrate` لا يفعل شيئًا | يعمل فعليًا |
